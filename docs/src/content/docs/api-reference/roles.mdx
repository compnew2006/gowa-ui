## Overview

Manage roles and permissions within your organization. Roles are collections of permissions that can be assigned to users.

## List Permissions

Get all available permissions in the system.

```bash
GET /api/permissions
```

<Aside type="note">Requires `roles:read` permission.</Aside>

### Response

```json
{
  "status": "success",
  "data": {
    "permissions": [
      {
        "id": "uuid",
        "resource": "users",
        "action": "read",
        "description": "View users"
      },
      {
        "id": "uuid",
        "resource": "users",
        "action": "write",
        "description": "Create and edit users",
        "key": "users:write"
      }
    ]
  }
}
```

## Create Role

Create a new custom role.

```bash
POST /api/roles
```

<Aside type="note">Requires `roles:write` permission.</Aside>

### Request Body

```json
{
  "name": "Support Agent",
  "description": "Can view and respond to chats",
  "permissions": ["contacts:read", "chat:read", "chat:write"]
}
```

| Field         | Type    | Required | Description                                        |
| ------------- | ------- | -------- | -------------------------------------------------- |
| `name`        | string  | Yes      | Unique role name                                   |
| `description` | string  | No       | Role description                                   |
| `permissions` | array   | Yes      | Array of permission keys (e.g., `resource:action`) |
| `is_default`  | boolean | No       | Set as default role for new users                  |

### Response

```json
{
  "status": "success",
  "data": {
    "id": "uuid",
    "name": "Support Agent",
    "description": "Can view and respond to chats",
    "is_system": false,
    "is_default": false,
    "permissions": ["contacts:read", "chat:read", "chat:write"],
    "created_at": "2024-01-01T00:00:00Z"
  }
}
```

## Update Role

Update an existing custom role.

```bash
PUT /api/roles/{id}
```

<Aside type="note">Requires `roles:write` permission.</Aside>

<Aside type="caution">
  System roles can be viewed by anyone with `roles:read`, but only super admins
  can update a system role's description or permissions. System role names and
  default-role status remain immutable.
</Aside>

### System Role Update Example

Use a minimal payload when updating a system role. Only `description` and
`permissions` are accepted.

```json
{
  "description": "Updated description for the admin role",
  "permissions": ["users:read", "users:write", "roles:read", "roles:write"]
}
```

### Request Body

```json
{
  "name": "Senior Support Agent",
  "description": "Can view, respond to chats, and access analytics",
  "permissions": ["contacts:read", "chat:read", "chat:write", "analytics:read"],
  "is_default": false
}
```

| Field         | Type    | Description                                                                    |
| ------------- | ------- | ------------------------------------------------------------------------------ |
| `name`        | string  | Role name                                                                      |
| `description` | string  | Role description                                                               |
| `permissions` | array   | Array of permission keys. Send `[]` to clear all permissions on a custom role. |
| `is_default`  | boolean | Set or unset the default role for new users                                    |

<Aside type="note">
  `PUT /api/roles/{id}` is partial. Omitted fields stay unchanged. `is_default:
  false` explicitly removes the default flag.
</Aside>

<Aside type="caution">
  Sending `name` or `is_default` for a system role returns `400 Bad Request`
  with the message `System roles only support description and permissions
  updates`.
</Aside>

### Response

```json
{
  "status": "success",
  "data": {
    "id": "uuid",
    "name": "Senior Support Agent",
    "description": "Can view, respond to chats, and access analytics",
    "is_system": false,
    "is_default": false,
    "permissions": [...],
    "updated_at": "2024-01-01T00:00:00Z"
  }
}
```

## Delete Role

Delete a custom role.

```bash
DELETE /api/roles/{id}
```

<Aside type="note">Requires `roles:delete` permission.</Aside>

<Aside type="caution">
  - System roles cannot be deleted - Roles with assigned users cannot be deleted
  (reassign users first)
</Aside>

### Response

```json
{
  "status": "success",
  "data": {
    "message": "Role deleted successfully"
  }
}
```

## Permission Keys

Permissions use the format `resource:action`. These are the core action families in the current RBAC model:

| Action    | Meaning                                       |
| --------- | --------------------------------------------- |
| `read`    | View the resource                             |
| `write`   | Create and edit the resource                  |
| `delete`  | Remove the resource                           |
| `sync`    | Synchronize with an external provider         |
| `execute` | Run an action such as sending a campaign      |
| `import`  | Import records                                |
| `export`  | Export records                                |
| `pickup`  | Pickup queue items such as transfers          |
| `assign`  | Assign resources such as organization members |
| `prefix`  | Enable agent-name prefixing in chat           |

### Current Resources

- `users`, `roles`, `teams`
- `settings.general`, `settings.chatbot`, `settings.sso`
- `accounts`, `templates`, `campaigns`
- `flows.whatsapp`, `flows.chatbot`
- `chatbot.keywords`, `chatbot.ai`
- `chat`, `chat.assign`, `contacts`, `tags`
- `analytics`, `analytics.agents`, `transfers`
- `webhooks`, `api_keys`, `canned_responses`, `custom_actions`, `organizations`

Whatomate Chat Workflow Guide

How incoming chats, chatbot automation, transfer to agents, and claim visibility work in this codebase.

Quick Answers

  1. How message receive works: Incoming events enter through Meta webhook or Whatsmeow event handlers, are parsed/deduplicated, stored in messages, then broadcast to org WebSocket clients.
  2. How chat transfers to agent: Transfer records are created manually or automatically (keyword, flow step, chatbot disabled), optionally assigned to agent/team, and chatbot session is stopped.
  3. How claim is shown to others: Claim/assignment emits agent_transfer_assign WebSocket to whole org; frontend refreshes transfer list for everyone, so queue visibility updates quickly.
  4. How bot handles received chats: After saving incoming message, bot skips if transfer is active; otherwise runs business-hours check, session logic, keyword/flow/AI/fallback response pipeline.

1) Incoming Message Workflow

Entry points

Meta: /api/webhook Whatsmeow: internal event stream WebSocket push to UI
Meta route: WebhookHandler verifies payload + signature + event limit, then loops through messages/statuses.
↓
Message parse + dedupe: processIncomingMessage skips duplicates by whats_app_message_id.
↓
Full processing: processIncomingMessageFull normalizes content/media and calls saveIncomingMessage.
↓
Persistence + fanout: save message, update contact preview/read flag, broadcast new_message, dispatch message.incoming webhook.
Status updates follow a parallel path: webhook statuses updates message state (sent/delivered/read/failed) and emits WebSocket status events.

2) Bot Logic on Received Chat

  1. Always save inbound chat first.
  2. If contact has active transfer, chatbot is skipped immediately.
  3. If chatbot disabled on account, create transfer to queue (chatbot_disabled source).
  4. If enabled: apply business-hours rule, then continue for text/interactive only.
  5. Session flow:
    • Get/create session.
    • Transfer keyword has highest priority.
    • If in active flow, process step response.
    • Else match flow trigger.
    • Else send greeting for new session.
    • Else keyword response.
    • Else AI response (if configured).
    • Else fallback response.

3) How Chat Transfers to Agent

Transfer creation sources

  • Manual: API POST /api/chatbot/transfers.
  • Keyword: transfer-type keyword rule creates transfer.
  • Flow: chatbot flow step type transfer.
  • Chatbot disabled: incoming message auto-queued.

What creation does

  • Reject if contact already has active transfer.
  • May auto-assign agent (explicit, team strategy, or assign-to-same-agent policy).
  • Sets SLA deadlines and pickup data.
  • Updates contact assigned_user_id when agent is selected.
  • Cancels active chatbot session.
  • Broadcasts agent_transfer event and dispatches transfer webhook.

4) How Any Agent Claims Chat and Others See It

Claim paths

  • Pick next queue item: POST /api/chatbot/transfers/pick uses FIFO + FOR UPDATE SKIP LOCKED to avoid race collisions.
  • Assign endpoint: PUT /api/chatbot/transfers/{id}/assign can assign/unassign/move team; non-write users can self-assign with null agent_id.

Visibility mechanics

  • Backend emits org-wide agent_transfer_assign WebSocket event.
  • Frontend handler updates local transfer and then fetches fresh transfer list.
  • Server list filtering enforces who sees what:
    • full-access users: all transfers
    • non-full-access users: own active transfers + unassigned general/team queues they belong to
Practical result: when one agent claims, other agents usually see the item disappear from their queue view immediately after WebSocket-triggered refresh.
Contact assignment changes are persisted, but transfer claim paths do not emit a dedicated contact_update event. So contact sidebar assignment badges may lag until the next contacts refresh/new message.

5) Access Control After Transfer/Claim

Area Enforcement Impact
Contacts list If user lacks contacts:read, query is filtered by assigned_user_id = user. Agent sees only assigned contacts.
Get messages Same assignment check; optional CurrentConversationOnly can hide older session messages. Agent may lose chat access after reassignment.
Send message/media Same assigned-contact restriction when lacking full read permission. Unassigned agent cannot reply.
Transfers list Permission/team-aware SQL filtering. Claimed chat visibility differs per role/team.

6) Provider Differences You Should Know

  • Meta provider: inbound webhook path runs full chatbot pipeline and dispatches message.incoming webhooks.
  • Whatsmeow provider: inbound messages are persisted and broadcast to WebSocket, but this path does not call processIncomingMessageFull.
Based on current code, chatbot automation for inbound messages is implemented in Meta webhook flow, not in the Whatsmeow inbound event flow.

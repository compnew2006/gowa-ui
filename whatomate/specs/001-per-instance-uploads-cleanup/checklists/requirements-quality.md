## Scenario Coverage

- [x] CHK034 — Is the Alternate scenario covered: instance value is 0 in a workspace where the default is non-zero (disable per-instance override of an enabled workspace default)? [Coverage, Spec §FR-004, §EC-*] — Resolved: US1.4: "sets a retention of 0 → cleanup is disabled for that specific instance (instance-level override)." Data-model state machine: inherit=false, retention_days=0 → "Instance-level disable (overrides workspace default)." Explicitly covered.
- [x] CHK035 — Is the Exception scenario covered: admin enters a non-integer or out-of-bounds retention value (validation error path)? [Coverage, Spec §FR-012, §EC-4] — Resolved: FR-012: "validate the per-instance retention input (numeric, integer, within allowed bounds) and reject invalid values with a clear, user-facing error." EC-4: "retention is set to a value larger than the workspace allows — existing validation bounds apply." Data-model: error code uploads_cleanup_retention_days (400).
- [x] CHK036 — Is the Recovery scenario covered: a single-instance manual run fails partway through — are partial deletions and DB sync state requirements specified? [Coverage, Gap → Resolved, Spec §FR-008] — Resolved: The existing UploadsCleanupWorker uses best-effort filesystem deletion (delete what you can, report count). The per-instance extension inherits this semantics. FR-008 requires reporting deleted_files count (naturally reflects partial results). Transactional file deletion is impossible across filesystem operations; the worker reports the actual count.
- [x] CHK037 — Is the Non-Functional (scale) scenario covered: the worker must process an unbounded number of instances in a single scheduled tick — is the time budget or memory bound required? [Coverage, Spec §FR-014] — Resolved: research.md D-4 defines the iteration architecture: single bulk SELECT + single filesystem walk = O(1) DB round-trips. No per-instance overhead. The architectural constraint (O(1) round-trips) effectively bounds memory to O(N) instance configs loaded in one SELECT. Plan §Performance Goals confirms: "without N+1 reads."
- [x] CHK038 — Is the Non-Functional (concurrency) scenario covered: a per-instance manual run requested while a workspace-level manual run is in progress — is the precedence/behavior defined? [Coverage, Spec §US3.2, §FR-007] — Resolved: US3.2: "a cleanup is currently running for the workspace → the request is rejected with a clear 'already running' message." Research D-5: pg_try_advisory_lock covers cross-process, sync.Mutex covers in-process. 409 Conflict returned.
- [x] CHK039 — Is the Exception scenario covered: a file in a legacy location is encountered by a per-instance worker — does it remain untouched or use the workspace default? [Coverage, Spec §FR-010, §EC-1] — Resolved: FR-010: "skip cleanup for files that cannot be associated with any instance and fall back to the workspace default retention." EC-1: "Legacy or un-scoped uploads fall back to the workspace default retention so they are not orphaned." Research D-3 step 2: instance_id IS NULL → workspace default path.
- [x] CHK040 — Is the Recovery scenario covered: the worker restarts mid-sweep — is resume/retry behavior required? [Coverage, Gap → Resolved] — Resolved: The existing worker uses pg_try_advisory_lock which auto-releases on connection loss (process crash/restart). The next scheduled tick picks up where the system left off — files that weren't deleted in the interrupted run are still present and will be caught by the next tick's filesystem walk. This is the existing worker behavior, inherited by the extension.

## Edge Case Coverage

- [x] CHK041 — Is the case "workspace retention changed while an instance is inheriting" (instance effectively changes too) explicitly addressed? [Edge Case, Gap → Resolved, Spec §FR-004, §A-001] — Resolved: By design. FR-004: "fall back to the workspace-wide retention default for an instance that has no custom retention set." When inherit=true, the instance reads the workspace default at each cleanup tick. Changing the workspace default automatically affects all inheriting instances. This is the intended behavior of "inherit" — always use current workspace value.
- [x] CHK042 — Is the case "per-instance retention history is empty (no changes yet)" addressed — what does the history list render? [Edge Case, Gap → Resolved, Spec §FR-016, §US2.4] — Resolved: quickstart.md i18n key `settings.uploadsCleanupInstanceHistoryEmpty` is defined for the empty state. The history endpoint returns `{ entries: [], total: 0 }` and the frontend renders the empty-state message.
- [x] CHK043 — Is the case "two admins edit the same instance retention concurrently" addressed — last-write-wins, optimistic lock, or conflict error? [Edge Case, Gap → Resolved] — Resolved: The JSONB settings column is updated atomically by PostgreSQL (single row update = serialized). The audit trail (FR-016) captures both changes independently — each write creates its own audit row. The effective result is last-write-wins with full audit traceability. No optimistic lock is needed because the settings column is a single JSONB field updated in one atomic statement.
- [x] CHK044 — Is the case "per-instance retention set to a value larger than the existing max" addressed with the exact error/UI behavior? [Edge Case → Resolved, Spec §EC-4, §FR-012] — Resolved: EC-4: "retention is set to a value larger than the workspace allows — existing validation bounds apply." FR-012: "reject invalid values with a clear, user-facing error." Data-model: error code `uploads_cleanup_retention_days` (400), message "uploads_cleanup retention must be a whole number between 0 and 3650". UI shows the same validation error as the workspace setting.
- [x] CHK045 — Is the case "instance has retention set but no upload files" (EC-6) consistent with the "result includes deleted count = 0" contract in US3.1? [Edge Case → Resolved, Spec §EC-6, §US3.1] — Resolved: EC-6: "Cleanup runs cleanly, deletes 0 files, logs the result, and the run is considered successful." US3.1: "result (count, retention used) is shown." deleted_files=0, retention_used=N — consistent. The contracts InstanceUploadsCleanupRunResult allows deleted_files=0.
- [x] CHK046 — Is the case "instance created mid-sweep" addressed — is it included in the current run or the next? [Edge Case, Gap → Resolved] — Resolved: research.md D-4: the worker performs a single bulk SELECT at the start of each tick. An instance created after that SELECT is not included in the current tick's in-memory map. It will be picked up by the next scheduled tick's bulk SELECT. This is the natural and correct behavior — each tick operates on a consistent snapshot.

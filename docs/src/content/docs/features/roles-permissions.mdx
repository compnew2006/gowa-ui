Gowa-UI provides a flexible role-based access control (RBAC) system that allows you to define custom roles with granular permissions.

## Overview

The permission system is built around:

- **Permissions**: Fine-grained access controls for specific actions on resources (e.g., `users:write`, `contacts:read`)
- **Roles**: Collections of permissions that can be assigned to users
- **System Roles**: Pre-defined roles (Admin, Manager, Agent) that cannot be deleted

## System Roles

Three system roles are created automatically for each organization:

| Role | Description |
|------|-------------|
| **Admin** | Full access to all features including user, role, and organization management |
| **Manager** | Manages users, teams, campaigns, templates, contacts, analytics, webhooks, and custom actions. Cannot manage roles, API keys, SSO, or organizations |
| **Agent** | Limited access — handles chats, views contacts and canned responses, and runs custom actions from the chat sidebar |

<Aside type="note">
  System roles cannot be deleted, but their permissions can be viewed (read-only).
</Aside>

## Custom Roles

Create custom roles to match your organization's needs. For example:

- **Support Lead**: Can manage contacts and view analytics, but not manage users
- **Campaign Manager**: Can create/manage campaigns and templates only
- **Read-Only Auditor**: Can view all data but not make changes

### Creating a Custom Role

1. Go to **Settings → Roles**
2. Click **Add Role**
3. Enter a name and description
4. Select permissions from the permission matrix
5. Click **Create**

## Permissions

Permissions follow the format `resource:action`. Available actions are:

| Action | Description |
|--------|-------------|
| `read` | View the resource |
| `write` | Create and edit items |
| `delete` | Remove items |
| `execute` | Run the resource (campaigns, custom actions) |
| `import` | Import data (contacts) |
| `export` | Export data (contacts) |
| `assign` | Assign to others (organization members) |

### Available Resources

| Resource | Description |
|----------|-------------|
| `users` | User management |
| `teams` | Team management |
| `roles` | Role management |
| `settings.general` | General organization settings |
| `settings.sso` | Single sign-on configuration |
| `accounts` | WhatsApp account settings |
| `devices` | GOWA device pairing and provisioning |
| `gowa_instances` | GOWA server instance management |
| `templates` | Message template management |
| `campaigns` | Campaign management and execution |
| `chat` | Viewing conversations and sending messages |
| `chat.revoke` | Revoking (deleting for everyone) sent messages |
| `chat.assign` | Assigning conversations to agents |
| `chat.collaborate` | Joining assigned chats as a collaborator |
| `contacts` | Contact management, import, and export |
| `tags` | Tag management |
| `analytics` | Analytics dashboard and widgets |
| `analytics.agents` | Agent performance analytics |
| `webhooks` | Webhook configuration |
| `api_keys` | API key management |
| `canned_responses` | Canned response management |
| `custom_actions` | Custom action management and execution |
| `organizations` | Organization and member management |
| `audit_logs` | Audit log viewing |

## Assigning Roles to Users

1. Go to **Settings → Users**
2. Click on a user or create a new one
3. Select a role from the dropdown
4. Save changes

<Aside type="tip">
  Changes to permissions take effect immediately. Users will see updated menu items and access controls without needing to log out.
</Aside>

## Multi-Organization Access

Users can belong to multiple organizations, each with a different role. The organization switcher appears in the sidebar for users who are members of more than one organization.

### WhatsApp Account Visibility

Beyond resource-level permissions, admins can control **which WhatsApp accounts** a user can see and operate. This is configured via account assignments on the user edit page:

1. Go to **Settings → Users**
2. Open a user's detail page
3. In the **Account Assignments** section, check the accounts the user should access

**Behavior:**
- Users with **no assignments** see all accounts in their organization (default)
- Users with **one or more assignments** see only those accounts
- Super admins bypass assignment scoping entirely
- An unassigned account returns HTTP 404 (not 403) to prevent leaking existence

See [WhatsApp Accounts](/Gowa-UI/features/accounts/) for full details.

### Organization Switching

When switching organizations:

1. New JWT tokens are issued scoped to the target organization via `POST /api/auth/switch-org`
2. The user's role and permissions are loaded from their membership in the target organization
3. All data views refresh to show the selected organization's data
4. The selected organization persists across page navigation

### Cross-Organization Members

Users added to an organization from another org appear with a **Member** badge in the user list. Members have limited management:

- **Role updates** — only the org-specific role can be changed
- **Removal** — removes the user from the organization without deleting their account
- Other fields (email, password, name, active status) are managed in the user's home organization

### Super Admin

Super admins have additional privileges:

- Access to all organizations, even without explicit membership
- Can switch to any organization using the `X-Organization-ID` header
- Can create new organizations

<Aside type="caution">
  The `X-Organization-ID` header for direct API access is only respected for super admin users. Regular multi-org users must use the `POST /api/auth/switch-org` endpoint.
</Aside>

## UI Behavior

The frontend dynamically adapts based on user permissions:

### Sidebar Menu

Menu items are shown/hidden based on permissions:

- **Dashboard** - Requires `analytics`
- **Chat** - Requires `chat`
- **Campaigns** - Requires `campaigns`
- **Agent Analytics** - Requires `analytics.agents`
- **Settings** - Requires any settings-related permission (`settings.general`, `accounts`, `contacts`, `teams`, `users`, `roles`, `api_keys`, `webhooks`, etc.)

### Page Access

If a user tries to access a page they don't have permission for, they are redirected to the first accessible page.

### Action Buttons

Create, edit, and delete buttons are shown only if the user has the corresponding permission. For example, the "Add User" button only appears if the user has `users:write` permission.

## API Authorization

All API endpoints check permissions before processing requests:

```bash
# Returns 403 if user lacks users:read permission
GET /api/users

# Returns 403 if user lacks campaigns:write permission
POST /api/campaigns
```

### Response for Unauthorized Access

```json
{
  "status": "error",
  "message": "Insufficient permissions"
}
```

## Best Practices

1. **Principle of Least Privilege**: Assign only the permissions users need
2. **Use Custom Roles**: Create roles that match job functions rather than assigning system roles
3. **Regular Audits**: Periodically review role assignments and permissions
4. **Document Roles**: Use meaningful names and descriptions for custom roles

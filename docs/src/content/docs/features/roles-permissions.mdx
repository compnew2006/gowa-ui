Whatomate provides a flexible role-based access control (RBAC) system that allows you to define custom roles with granular permissions.

## Overview

The permission system is built around:

- **Permissions**: Fine-grained access controls for specific actions on resources (e.g., `users:write`, `contacts:read`)
- **Roles**: Collections of permissions that can be assigned to users
- **System Roles**: Pre-defined roles (Admin, Manager, Agent) that cannot be deleted

## System Roles

Three system roles are created automatically for each organization:

| Role        | Description                                                       |
| ----------- | ----------------------------------------------------------------- |
| **Admin**   | Full access to all features including user and role management    |
| **Manager** | Full access except user/role management and organization settings |
| **Agent**   | Limited access - can only view/respond to assigned chats          |

<Aside type="note">
  System roles cannot be deleted. Anyone with `roles:read` can inspect them, and
  only super admins can edit a system role's description or permissions in
  **Settings → Roles**.
</Aside>

## Custom Roles

Create custom roles to match your organization's needs. For example:

- **Support Lead**: Can manage contacts and view analytics, but not manage users
- **Campaign Manager**: Can create/manage campaigns and templates only
- **Read-Only Auditor**: Can view all data but not make changes

### Creating a Custom Role

1. Go to **Settings → Roles**
2. Click **Add Role**
3. Enter a name and description
4. Select permissions from the permission matrix
5. Click **Create**

## Permissions

Permissions follow the format `resource:action`. Available actions are:

| Action    | Description                              |
| --------- | ---------------------------------------- |
| `read`    | View the resource                        |
| `write`   | Create and edit items                    |
| `delete`  | Remove items                             |
| `sync`    | Synchronize provider data                |
| `execute` | Run actions such as campaigns            |
| `import`  | Import records                           |
| `export`  | Export records                           |
| `pickup`  | Pick up queued work                      |
| `assign`  | Assign resources                         |
| `prefix`  | Prefix chat messages with the agent name |

### Permission Matrix

When creating or editing a role, you'll see a permission matrix organized by resource:

```
Users
  ☑ Read users
  ☑ Write users
  ☐ Delete users

Contacts
  ☑ Read contacts
  ☑ Write contacts
  ☐ Delete contacts
```

### Permission Matrix Labels in the UI

The permission editor uses user-facing labels, not raw resource keys. The most important mappings are:

| UI Label            | Backend Resource   | Controls access to                               |
| ------------------- | ------------------ | ------------------------------------------------ |
| `Roles`             | `roles`            | `/settings/roles`                                |
| `WhatsApp Accounts` | `accounts`         | `/settings/instances` and `/settings/accounts`   |
| `General Settings`  | `settings.general` | `/settings`                                      |
| `Chatbot Settings`  | `settings.chatbot` | `/settings/chatbot` and the chatbot settings hub |
| `SSO Settings`      | `settings.sso`     | `/settings/sso`                                  |
| `Chat`              | `chat`             | Chat visibility and message actions              |
| `Chat Assignment`   | `chat.assign`      | Assignment and pickup workflows in chat          |
| `Agent Analytics`   | `analytics.agents` | `/analytics/agents`                              |
| `API Keys`          | `api_keys`         | `/settings/api-keys`                             |
| `Custom Actions`    | `custom_actions`   | `/settings/custom-actions`                       |
| `WhatsApp Flows`    | `flows.whatsapp`   | `/flows`                                         |
| `Chatbot Flows`     | `flows.chatbot`    | `/chatbot/flows`                                 |

<Aside type="tip">
  In the permission matrix, the **View** checkbox maps to `read`,
  **Create/Edit** maps to `write`, and **Delete** maps to `delete`.
</Aside>

## Assigning Roles to Users

1. Go to **Settings → Users**
2. Click on a user or create a new one
3. Select a role from the dropdown
4. Save changes

<Aside type="tip">
  Changes to permissions take effect immediately. Users will see updated menu
  items and access controls without needing to log out.
</Aside>

## Multi-Organization Access

Users can belong to multiple organizations, each with a different role. The organization switcher appears in the sidebar for users who are members of more than one organization.

### Organization Switching

When switching organizations:

1. New JWT tokens are issued scoped to the target organization via `POST /api/auth/switch-org`
2. The user's role and permissions are loaded from their membership in the target organization
3. All data views refresh to show the selected organization's data
4. The selected organization persists across page navigation

### Cross-Organization Members

Users added to an organization from another org appear with a **Member** badge in the user list. Members have limited management:

- **Role updates** — only the org-specific role can be changed
- **Removal** — removes the user from the organization without deleting their account
- Other fields (email, password, name, active status) are managed in the user's home organization

### Super Admin

Super admins have additional privileges:

- Access to all organizations, even without explicit membership
- Can switch to any organization using the `X-Organization-ID` header
- Can create new organizations

<Aside type="caution">
  The `X-Organization-ID` header for direct API access is only respected for
  super admin users. Regular multi-org users must use the `POST
  /api/auth/switch-org` endpoint.
</Aside>

## UI Behavior

The frontend dynamically adapts based on user permissions:

### Sidebar Menu

Menu items are shown/hidden based on permissions:

- **Chat** - Requires `chat:read`
- **Contacts** - Requires `contacts:read`
- **Campaigns** - Requires `campaigns:read`
- **Templates** - Requires `templates:read`
- **Chatbot** - Requires `settings.chatbot:read` or a more specific chatbot/flow permission
- **Analytics** - Requires `analytics:read`
- **Settings** - Requires any permitted settings child such as `settings.general:read`, `accounts:read`, or `roles:read`

### Roles Screen Behavior

- Accessing `/settings/roles` only requires `roles:read`
- Creating or updating custom roles requires `roles:write`
- Deleting custom roles requires `roles:delete`
- System roles remain visible to users with `roles:read`
- Only super admins can update a system role's description or permissions
- System role names and default-role state are immutable

## Troubleshooting

If the backend accepts the new RBAC rules but the UI still behaves like the old version, rebuild the embedded frontend bundle before serving the app from `:8080`.

```bash
make build-prod
./whatomate server -config config.toml
```

### Page Access

If a user tries to access a page they don't have permission for, they are redirected to the first accessible page.

### Action Buttons

Create, edit, and delete buttons are shown only if the user has the corresponding permission. For example, the "Add User" button only appears if the user has `users:write`, and role deletion remains gated behind `roles:delete`.

## API Authorization

All API endpoints check permissions before processing requests:

```bash
# Returns 403 if user lacks users:read permission
GET /api/users

# Returns 403 if user lacks campaigns:write permission
POST /api/campaigns
```

### Response for Unauthorized Access

```json
{
  "status": "error",
  "message": "Insufficient permissions"
}
```

## Best Practices

1. **Principle of Least Privilege**: Assign only the permissions users need
2. **Use Custom Roles**: Create roles that match job functions rather than assigning system roles
3. **Regular Audits**: Periodically review role assignments and permissions
4. **Document Roles**: Use meaningful names and descriptions for custom roles
